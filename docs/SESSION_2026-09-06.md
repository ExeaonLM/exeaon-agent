## 1. Gateway: model-mapping cache (the DB outage fix)

**Symptom:** `litellm ... 查询模型映射失败 ... failed SASL auth: unexpected EOF`
on every inference request.

**Root cause:** **Postgres, not Redis.** `resolveModelMapping` in
`internal/biz/gateway.go` queried Postgres on *every* proxied request with no
cache. The Fly DB (`exeaon-claw-db`) is `shared-cpu-1x:256MB` — under load it hit
its connection/memory ceiling and dropped connections mid-SASL. The DB was
*healthy*, just choking on per-request load.

**Fix (`98029da`, deployed Fly v24):** a resolution cache mirroring `key_cache.go`:
- `internal/biz/model_mapping_cache.go` (new): L1 `sync.Map` per virtual-key ID
  (60s TTL) → L2 Redis `ai:gw:mapping:<keyID>` (5min) → DB, with pub/sub
  invalidation (`ai:gw:mapping:invalidate`) for cross-instance flush.
- `gateway.go`: `resolveModelMapping` → `loadMappingsForKey` (L1→L2→DB);
  `StartModelMappingCacheInvalidator` registered in `StartBackgroundWorkers`.
- `model_mapping_admin.go`: Create/Update/Delete invalidate the cache (a global
  `vk=0` mapping flushes all; a per-key mapping invalidates just that key).

**Effect:** removes the per-request DB hit; a warm cache serves last-known
mappings through a DB blip ("fail open on economics").

**Still recommended:** bump the DB to ≥512MB (`flyctl machine update <id>
--vm-memory 1024 -a exeaon-claw-db`) for headroom.

**Separately diagnosed (real problem now):** most runs fail with upstream **429**
because `Exeaon Video 1.0` maps to the free `minimax/minimax-m3:free` (shared
pool), with **no fallback chain**. Fix = add a fallback chain / BYOK key / paid
model to that mapping in the console. *Not yet done.*

## 2. Desktop: agent-server 401 auto-recovery

**Symptom:** `Request failed with status code 401` toast; sidebar/conversations
fail to load.

**Root cause:** the **local agent-server** rotates its session API key on restart;
the running app holds the stale key. The key is delivered only at page-serve time
(baked `VITE_SESSION_API_KEY` in dev, injected `window.__AGENT_CANVAS_SESSION_API_KEY__`
in the packaged app), so it can only be refreshed by a page reload.

**Fix (`de5ebfab1` + `fcbdf01da`, `query-client-config.ts`):** on a local-backend
401, reload once to pick up a fresh key. Guards (the `fcbdf01da` fix corrected an
initial reload-loop bug):
- **Dev-gated** — in dev the key is baked into the bundle, so a reload can't
  refresh it; auto-reload is disabled there (a 401 just toasts).
- **One reload per episode** (sessionStorage guard) — no loop if the reload
  doesn't fix it; falls through to a toast.
- **Cleared on the next successful response** — a genuine later rotation still
  gets its single recovery.
- Skips entirely if `sessionStorage` is unavailable (a toast beats a loop).

## 4. Bundling — `scripts/bundle-sim-deps.ps1` (`323b219a3`, `35bb73724`)

One idempotent pre-`tauri build` step that stages sim deps into the **bundled
runtime/resources** (never system Python) so packaged builds are offline:
- MuJoCo + numpy → `python-runtime` ✓
- Icarus Verilog → `resources/mcp/iverilog` ✓ (the rtl-sim server searches
  `../iverilog/bin`)
- CybORG → `python-runtime` — **fails, and that's expected** (see below)

Sets `PYTHONNOUSERSITE=1` so installs land in the runtime's own (bundle-able)
site-packages, not the shared `%APPDATA%` user-site. Per-component `-Skip` flags;
bootstraps pip via `ensurepip` when the embedded runtime lacks it.

**Recommended invocation:** `pwsh -File scripts/bundle-sim-deps.ps1 -SkipCyborg`

**CybORG can't be bundled on Python 3.14:** it pins old deps (`numpy==1.26.4`,
`gym 0.26.2`, `matplotlib 3.8.2`, …) with no 3.14 wheels, so pip compiles them
from source — which the embedded runtime can't do (no dev headers / `pythonNN.lib`).
The script now treats this as a **warning, not a build-blocker**; cyber-sim stays
on-demand via its MCP's install hint. To actually bundle CybORG you'd need a
Python 3.11/3.12 runtime for it, or to modernise its pins.

## 5. Ops learnings (no code, but cost real time — now in memory)

- **Blank-window hang in dev = Windows Defender throttling vite.** Defender scans
  `node_modules` on every file access, making vite's dep-optimizer resolve
  5–10s *per module* (vs single-digit ms) — the dep-optimizer wedges and the app
  never paints. **Fix: Defender path exclusions** (the project, `%APPDATA%\Python`,
  the Python installs) + process exclusions (node/python/cargo/esbuild). **Do not
  delete `node_modules/.vite`** — it forces a full cold re-optimize that crawls
  under AV.
- **The dev app 401** was the local agent-server, not the cloud (now auto-recovered).
- **Dev is slow to open by nature** — vite ~30s + Rust compile; the packaged app
  is fine. Not a bug.
